# Repository Mission — Layer Separation

```text
NOTION      architecture, ADRs, communication, strategic context
SPECIFY-CLI specs/<feature>/  requirements, plans, tasks, contracts, acceptance criteria
REPOSITORY  implementation, tests, fixtures, schemas, executable artifacts
MEMORY      forge-mind-scoped ONLY: docs/CURRENT_STATE.md, docs/FAILURE_LOG.md,
            docs/decisions/, and (future) a forge-mind-scoped ChromaDB via MCP
```

Never confuse these layers. Never store ForgeMind engineering facts in
universal Hermes profile memory (MEMORY.md/USER.md).

This file complements `AGENTS.md` (which is loaded automatically and governs
coding-agent behavior). When the two disagree, surface it as drift.

# Session Startup Protocol

At the start of significant work:

## Step 1 — Read State of Record FIRST
Read `docs/CURRENT_STATE.md`. It is the authoritative operational state:
current phase, what works, verification results, next task, blockers.

## Step 2 — Inspect the Repository
Identify structure, branch/state, active specifications under `specs/`, source
under `src/forgemind/`, tests under `tests/{contract,integration}/`, fixtures
under `fixtures/{inputs,expected}/`. Do not assume structure — inspect it.

## Step 3 — Locate the Active Specification
Canonical home is `specs/<feature>/` (currently
`specs/001-hierarchical-runtime-dag/`). Determine: which spec is active, which
phase per `plan.md`, which task per `tasks.md`, what prerequisites are
complete, what is blocked. Prefer current specs over historical memory.
Check `docs/decisions/` before assuming any unresolved architectural decision.

## Step 4 — Retrieve Relevant Project Memory
Only what is relevant to the task: recent state, related failures
(`docs/FAILURE_LOG.md`), relevant decisions. Do not retrieve everything.

## Step 5 — Reconcile Memory with Reality
If memory claims "Task X completed" but the repository does not support it:

```text
STATUS = DRIFT DETECTED
```

Never silently trust memory over the repository.

# Planning Protocol

Before recommending implementation:

1. Identify the target: current phase, active specification, current task.
2. Identify constraints: architectural invariants, acceptance criteria,
   dependencies, required contracts, existing tests, fixture requirements.
3. Identify the smallest valid increment — one coherent vertical slice that
   moves the project forward without architectural debt. No scope creep.
4. Produce the plan containing: Goal, Current State, Evidence, Constraints,
   Files/Components Affected, Dependencies, Implementation Steps,
   Verification Steps, Completion Criteria, Risks, Next State.

Prefer small / verifiable / reversible / well-scoped over large /
speculative / architecture-changing / unverified.

# Verification Protocol

When reviewing completed work, verify layer by layer:

## Layer 1 — Structural
Required files exist; paths match specification; schemas exist (`contracts/`);
fixtures exist; tests exist.

## Layer 2 — Contract
Schemas valid (draft-07); fixtures conform; references valid; required fields
present; enums match spec; provenance preserved.

## Layer 3 — Architectural
Supervisor cannot become a specialist; Manager cannot become a cross-domain
validator; Workers cannot spawn workers or make decisions; Validator cannot
autonomously act; Reducer cannot bypass ValidatedSituation.

## Layer 4 — Specification
For each acceptance criterion: Criterion / Evidence / Status / Gap. Verdicts:
PASS | WARNING | FAIL | BLOCKED | UNKNOWN. Never convert UNKNOWN into PASS.

## Layer 5 — Regression
What existing behavior could this change break? Check fixtures, contract
compatibility, tests, provenance, previously recorded failures.

Verification commands (from repo root):

```bash
pytest tests/
PYTHONPATH=src python -c "import forgemind"
python scripts/run_fixture.py            # batch
python scripts/run_fixture.py fixtures/inputs/FIXTURE-001-happy-path.json
```

requires it.

# Drift Detection Protocol

Detect and report these patterns explicitly:

```text
Architecture Drift:     ADR/architecture != specification
Specification Drift:    specification     != implementation
Implementation Drift:   implementation    != tests/fixtures
Memory Drift:           project memory    != current repository
Documentation Drift:    Notion comms      != approved architecture / current phase
```

Report format:

```text
DRIFT TYPE: <type>
Expected: <...>
Observed: <...>
Evidence: <files/tests>
Impact: <...>
Recommended Resolution: <...>
Blocking: YES|NO
```

# Completion Protocol

Before declaring work complete:

1. Check the specification and its acceptance criteria.
2. Inspect the repository.
3. Run or inspect relevant verification (commands above).
4. Check regression risk against existing behavior and past failures.
5. Update project memory IN THE REPO (docs/CURRENT_STATE.md;
   docs/FAILURE_LOG.md on failure) per AGENTS.md documentation rules.
6. Report remaining uncertainty explicitly.

Completion requires evidence.

# Non-Negotiable Rules

Never:

- invent repository state or claim code exists without evidence
- mark planned work as implemented, or implementation as verified without evidence
- silently resolve architectural contradictions
- bypass specify-cli specifications
- allow a Worker to become a decision maker
- allow the Validator to autonomously execute actions
- allow the Decision Reducer to bypass the ValidatedSituation boundary
- write ForgeMind engineering facts into universal Hermes profile memory
- confuse Notion's Golden Demo fixture with repository contract fixtures

# Final Principle

The repository is a chain of engineering truth:

```text
INTENT -> SPECIFICATION -> PLAN -> TASK -> IMPLEMENTATION -> VERIFICATION
       -> EVALUATION -> MEMORY
```

Keep every link connected. When uncertain: inspect. When sources disagree:
report drift. When planning: minimize scope. When verifying: require
evidence. When progress is made: preserve the learning.
